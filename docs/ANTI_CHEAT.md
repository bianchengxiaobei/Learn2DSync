# 反外挂现状评估与改进路线

日期：2026-11-03  
适用版本：v1.74 / 协议 v9 / 快照 v7  
状态：仅评估，未修改代码

本文只讨论与网络同步相关的反外挂能力。客户端渲染、注入、账号体系和平台级反作弊只在边界处提及。

> 说明：文中的行号基于 2026-11-03 的 v1.74 代码，后续改动后请以函数名为准重新定位。

---

## 1. 结论摘要

这套同步模型的攻击面很小：客户端只能发送 18 字节的输入载荷（`slot/sequence/buttons/aim_x/aim_y/tick/actions/action_toggles/action_param/reserved`，加 20 字节包头），移动、射击、伤害、比分全部由服务器计算。因此**状态类作弊基本被阻断**。

但当前所有校验都停在“语法层”：

- 服务器只检查输入字段是否合法，不检查输入意图是否合理（瞄准是否可见、反应是否非人类、tick 是否诚实）。
- 世界状态是**全量广播**，且为了远端预测会把所有玩家的原始输入广播给所有客户端。
- 会话 token 是自增 32 位，重连只凭 token，传输无加密无 MAC。
- 登录包在限流之前处理，且没有身份认证。

一句话：**现阶段更像“防不同步、防协议滥用”，不是“防作弊”。** 好友局/局域网够用；公开匹配至少要先补 AOI/视野裁剪、瞄准校验、会话加密这三件事。

## 2. 信任边界与攻击面

### 2.1 客户端能控制什么

| 字段 | 客户端可控 | 服务器校验 | 说明 |
|---|---|---|---|
| `slot` | 是 | 必须等于会话 slot | 不能替别人发输入 |
| `buttons` | 是 | 只允许低 8 位（`0x00FF`） | Gadget2/3 通过 action 事件重建 |
| `aim_x/aim_y` | 是 | 只做归一化，不校验方向合理性 | 自瞄的核心入口 |
| `tick` | 是 | 窗口 `[server_tick - server_lag - 2, server_tick + 120]` | 输入时序作弊的入口 |
| `actions` | 是 | 最高位必须为 0；事件去重 | 动作事件与按钮状态做一致性检查 |
| `sequence` | 是 | 只在 action queue 去重用，不用于包排序/重放检测 | 重复包基本无害 |
| `LoginRequest` 里的 fingerprint | 是 | 只与服务器值比较 | 客户端自报，非可信证明 |
| `reconnect_token` | 是 | 只查是否存在 | 32 位自增，可枚举 |

代码位置：

- 包格式与上限：`src/net/protocol.h:11-13`
- 包编解码：`src/net/protocol.cpp:178-253`
- 输入编解码与基本校验：`src/net/protocol.cpp:645-682`
- 输入业务校验：`src/net/real_server.cpp:679-715`
- 输入窗口配置：`src/net/real_server.h:30-39`

### 2.2 服务器相信什么

服务器**不**相信客户端的位置、血量、弹药、伤害、比分。  
服务器**会**相信：

1. 客户端声明的 `tick`（在窗口内）。
2. 客户端声明的 map/content fingerprint（只做兼容性比较）。
3. 客户端上报的 ACK/Sync hash（只用于决定是否补发快照，不用于判定作弊）。
4. `reconnect_token` 能证明会话归属（实际上只证明“知道这个数字”）。

### 2.3 数据流

```text
Client A ── Input(buttons, aim, actions, tick) ──► Server
                                                      │
                          ┌───────────────────────────┤
                          │                           │
                          ▼                           ▼
              InputBroadcast(所有人)          Snapshot 20Hz(全量, 所有人)
                          │                           │
                          ▼                           ▼
              Client B/C 本地预测所有玩家      Client B/C 对账/回滚
```

- 服务器固定 60Hz，每 3 tick 发一次全量快照（`real_server.cpp:325-390`、`real_server.cpp:1716-1804`）。
- 登录包在会话查找和限流之前处理（`real_server.cpp:392-421`）。
- 服务器收到输入后立即广播给所有客户端（`real_server.cpp:1842-1868`）。
- 客户端本地模拟所有玩家（`local_net.cpp:492-537`），因此必然持有全部实体状态。

### 2.4 攻击面总结

1. **输入语义**：aim、tick、actions。
2. **信息面**：全量快照 + 输入广播 + 本地全玩家模拟。
3. **会话面**：自增 token、明文 UDP、登录无认证。
4. **资源面**：登录路径无限流、单包 128KB、全局 `waitsnd` 背压、late replay CPU 放大。
5. **客户端完整性**：无签名、无完整性校验、无注入防护。

## 4. 作弊类型逐项分析

### 4.1 状态类作弊（已阻断）

**攻击方式**：改内存改坐标、改血量、改弹药、改伤害、改比分、瞬移、加速。

**现状**：不可行。客户端只发按钮，服务器自己跑 `World::step()`。客户端的本地世界只是预测，最终由快照校正。

**残留问题**：

- 客户端可以拒绝接受快照校正，只影响自己，不影响服务器。
- 客户端可以伪造 ACK/Sync hash 来减少被校正的频率，但不会改变服务器的权威状态。

**结论**：这一类不需要额外投入。

---

### 4.2 自瞄 / 微自瞄 / 扳机机器人（可行，P0）

**攻击方式**：

1. 读取本地世界里的敌人位置（本来就有）。
2. 每帧把 `aim_x/aim_y` 指向敌人。
3. 准星覆盖时按 `fire`。

**现状**：

- `aim_x/aim_y` 是客户端给出的绝对方向，服务器只做 `normalized()`（`world.cpp:274-283`）。
- 服务器没有视线（LOS）、视野（FOV）、转向速率、反应时间校验。
- `fire` 只是按钮，服务器只限制武器射速/弹药，不判断“这一枪是否像人打出来的”。
- 弹道仍会被墙挡住，所以自瞄通常要等 LOS；但客户端知道所有敌人位置，可以做到“出掩体瞬间完美开枪”。

**影响**：高。竞技游戏里这是最核心的作弊类型。

**改进方向**（按侵入性排序）：

1. **服务器端 LOS/FOV 校验**：开火时检查 aim 方向是否指向可见敌人；不满足则拒绝该次射击或按普通方向发射。能抬高自瞄成本，但挡不住“等 LOS”的自瞄。
2. **转向速率上限**：限制每 tick 的 aim 角度变化（例如 20–40 度/tick），超过则钳制或标记。会误伤高灵敏度玩家，需要可配置和灰度。
3. **统计检测**：记录瞄准速度、准星到目标的距离、跟踪误差、反应时间、爆头率、预开火比例，离线/在线打分。
4. **服务器录像 + 人工复核**：现有确定性 replay 已经具备基础，建议把可疑对局的输入/快照落盘。
5. **不推荐**：让服务器接管瞄准（自动锁定），会改变手感，且不是本项目目标。

---

### 4.3 透视 / 雷达 / 弹道预警（可行，P0/P1）

**攻击方式**：读客户端内存或改渲染，把所有玩家/弹道画出来。

**现状**：

- 快照包含所有玩家的位置、速度、瞄准、按钮位和所有弹道（`snapshot.cpp:213-269`）。
- 服务器把每个玩家的原始输入广播给所有人（`real_server.cpp:1842-1868`）。
- 客户端为了预测远端玩家，必须本地模拟所有玩家（`local_net.cpp:492-537`）。

因此“敌人位置”在客户端是**设计上必须存在**的，不是漏洞。没有 AOI/可见性裁剪，服务器无法阻止客户端使用已经下发的数据。

**影响**：取决于玩法：

- 如果有战争迷雾/掩体遮挡：影响高，等同于透视。
- 如果本来就是全员可见的俯视竞技场：边际价值低，但仍能看到屏幕外/掩体后的信息。

**改进方向**：

1. **AOI/可见性裁剪**：服务器按客户端视野/距离/队伍过滤实体，只发可见实体和必要弹道。
2. **输入广播裁剪**：只广播 AOI 内玩家的输入；AOI 外的远端玩家改为快照插值。
3. **代价**：这会破坏“所有客户端本地预测所有玩家”的现状，需要改成“预测本地玩家 + 预测 AOI 内远端 + AOI 外插值/冻结”。这是架构级改动，需要单独设计。
4. **带宽收益**：全量快照 10 人约 2KB/20Hz（每客户端约 40KB/s）；AOI 后可以显著下降。

**注意**：AOI 与确定性回放有冲突。服务器录像仍然可以保留全量状态，但客户端不再拥有全量信息。

---

### 4.4 输入时序作弊（可行，P1）

**攻击方式**：

1. 客户端自己决定 `tick`。
2. 使用比诚实客户端更小的 lead（例如 1–2 tick），获得更低的权威延迟。
3. 或发送略早于 `server_tick` 的输入，服务器会把它夹到 `server_tick + 1` 立即执行（`real_server.cpp:744-765`）。
4. 在服务器模拟目标 tick 之前，反复覆盖同一个未来 tick 的输入（`session.pending_inputs[tick] = command`），实现“最后一刻改主意”。

**现状**：

- 服务器只校验窗口：早于 `server_tick - server_lag - 2` 或晚于 `server_tick + 120` 才拒绝。
- 没有强制最小 lead，也没有限制同一未来 tick 的覆盖次数。
- 诚实客户端用 `RTT/2 + 4` 的 lead（`real_client.cpp:295-310`），作弊客户端可以不用。

**影响**：中。不是“无敌”，但在对枪/抢点时有稳定的时序优势。

**改进方向**：

1. 服务器统一 lead：要求 `input.tick >= server_tick + min_lead`（例如 2–4 tick），拒绝“贴脸”输入。
2. 限制未来 tick 覆盖：同一 tick 只允许有限次覆盖，或只允许在特定窗口内覆盖。
3. 记录每个会话的 lead 分布，偏离正常值过多时标记。
4. 注意：这会增加诚实玩家的输入延迟，需要和手感一起调参。

---

### 4.5 late input replay 的“时光倒流”（默认关闭，开启后 P0）

**攻击方式**：

1. 看到子弹/击杀/控制点变化后，补发一个针对过去 tick 的输入。
2. 服务器 `replay_late_inputs` 会 restore 旧快照、重放所有玩家、重写快照历史（`real_server.cpp:1506-1696`）。
3. 作弊者的迟到输入可以改变已经发生的结果（躲子弹、撤销死亡、改占点）。

**现状**：

- 默认 `late_input_replay=false`（`real_server.h:35`），所以默认不可行。
- 一旦开启，窗口默认 120 tick（2 秒），放大效应明显。
- 服务器会忽略重写点之前的旧 ACK（`rewritten_ack_ignore_before_tick_`），但不会处罚发起者。

**建议**：

1. 保持默认关闭。
2. 如果必须开启，把窗口压到个位数 tick，并只允许“移动类”迟到输入，不允许开火/伤害类。
3. 记录每个会话的 late replay 次数和回滚距离，异常时告警。
4. 为 late replay 增加速率上限和总预算，防止 CPU 放大攻击。

---

### 4.6 宏 / 脚本 / 预输入（可行，P2）

**攻击方式**：

- `max_input_ahead_ticks=120`，作弊客户端可以一次性预填未来 2 秒的输入（不同 tick、不同 aim/按钮），形成脚本化连招。
- `sequence` 不用于包排序，重复包/重放包基本无害，但可以制造无效负载。
- 最后一次输入会持续生效：`session.input_state` 在每个 tick 都会被提交（`real_server.cpp:1482-1486`），所以发一次“按住开火”后停止发包，服务器仍会持续开火。

**影响**：中低。主要是自动化和“挂机输出”。

**改进方向**：

1. 限制未来输入的总量和密度（例如最多预填 10–20 tick）。
2. 要求输入包按 sequence 单调递增，重复/回退包计入异常。
3. 对“长时间无输入但按钮持续按住”的会话做标记或自动释放按钮。

---

### 4.7 会话与协议安全（可行，P0）

**攻击方式**：

1. session token 是自增 32 位（`real_server.cpp:313-323`），从 1 开始。
2. 重连只凭 `reconnect_token`，可以换 peer（`real_server.cpp:502-510`）；旧 peer 会被踢掉。
3. 协议明文，无 HMAC/加密（`protocol.cpp:178-253`）。
4. 嗅探或枚举 token 后，可以会话劫持、踢人、伪造输入。

**影响**：高。公开联机时这是“账号安全”级别的问题，不只是作弊。

**改进方向**：

1. 128-bit CSPRNG token（OS 随机源），协议字段扩展。
2. 包级 HMAC（至少防离线伪造）；更强的是 DTLS 或 libsodium 的 `crypto_kx + secretbox`。
3. token 绑定 peer（IP + 端口），重连换 token，缩短重连窗口。
4. 登录加入挑战/响应或平台票据，不再“报个数字就能接管”。
5. 当前 vcpkg 依赖里没有加密库（kcp 本身不带加密）；实现时需要新增 openssl 或 libsodium 依赖。

---

### 4.8 登录洪泛 / 占坑（可行，P0）

**攻击方式**：

1. `handle_message` 在查会话和限流之前就处理 `LoginRequest`（`real_server.cpp:392-421`）。
2. 每个新 peer 的登录都会创建一个会话并占用一个 slot（`real_server.cpp:512-588`）。
3. 攻击者用大量源端口发起登录，可以占满所有 slot，或制造 CPU/内存压力。

**影响**：高。这是低成本拒绝服务。

**改进方向**：

1. 登录路径加限流：按 IP、按全局、按时间窗口。
2. 未完成握手/未进入 Lobby 的会话设置短 TTL 和更小的配额。
3. slot 分配与“已认证会话”绑定，未认证连接不占正式 slot。
4. 监控 `logins`、失败率、每 IP 并发数。

---

### 4.9 DoS / 背压（可行，P0/P1）

**攻击方式**：

1. 单包上限 128KB（`protocol.h:12`），按 600 pps 可灌入大量数据。
2. 固定窗口限流在窗口边界可双倍突发（`rate_limit.h`）。
3. `send_snapshot_to_all` 用全局 `transport_.stats().waitsnd > 128` 直接跳过快照（`real_server.cpp:1717-1719`）；而服务器侧的 `waitsnd` 是所有 peer 的最大值（`kcp_transport.cpp:695-705`）。一个故意不 ACK 的慢客户端可以让**所有人的快照**停发。
4. late replay 的 CPU 放大（见 4.5）。

**改进方向**：

1. 按消息类型限制 payload（输入 ≤ 32B、快照 ≤ 8KB）。
2. 令牌桶限流，替代固定窗口。
3. 背压改成 per-peer：只跳过慢客户端的快照，不影响其他人。
4. 对长期 `waitsnd` 超限的 peer 降级或断开。
5. late replay 增加每 tick 总预算和全局预算。

---

### 4.10 客户端完整性（可行但暂不处理，P2）

**现状**：无签名、无完整性校验、无反调试、无注入防护。内存修改、DLL 注入、宏、录屏识别都可以做。

**建议**：

- 如果目标是公开竞技，最终需要平台级反作弊（EAC/BattlEye 类似方案）或自研驱动；成本高，不建议在服务器同步层解决。
- 服务器侧能做的是“行为检测 + 录像复核”，不要试图在客户端做可信检测。

---

### 4.11 指纹与内容校验（部分有效，P1）

**现状**：

- 登录时比较 `map_fingerprint` 和 `content_fingerprint`（`real_server.cpp:490-498`）。
- 但这是客户端**自报**的字段，作弊客户端可以发送服务器期望的值。
- 因此它只防“版本/地图不一致”，不防“改了客户端还来联机”。

**建议**：

- 明确文档定位：兼容性检查，不是完整性证明。
- 如果要做内容校验，需要服务器下发挑战、客户端返回带签名的资源哈希，或使用平台票据；单靠当前字段不可信。
- 至少把 fingerprint 不匹配的登录计入统计，便于发现异常客户端。

| 问题 | 说明 | 建议 |
|---|---|---|
| 输入持续生效 | 最后一次 `input_state` 每 tick 重复提交 | 长时间无新输入时释放按钮或标记 |
| `sequence` 未强制单调 | 重复/旧包不报错 | 会话内维护期望 sequence，回退计入异常 |
| ACK 可伪造 | 客户端可发匹配 hash 避免被同步 | 只用于校正，不用于处罚；记录异常 ACK 率 |
| 快照全量广播 | 无 delta、无 AOI | 见 4.3 |
| 无聊天/文本输入 | 暂无注入面 | 未来加聊天时注意转义与限流 |
| 观战/回放 | 当前无观战 | 未来观战必须做延迟和视角隔离，避免“观战透视” |

## 5. 风险矩阵

| 作弊类型 | 当前可行性 | 现有拦截 | 影响 | 优先级 |
|---|---|---|---|---|
| 改坐标/血量/弹药/伤害/比分 | 不可行 | 服务器权威 | — | — |
| 自瞄/微自瞄/扳机 | 可行 | 无 | 高 | P0 |
| 透视/雷达/弹道预警 | 可行 | 无（信息本来就下发） | 高（有遮挡玩法）/低（全员可见） | P0/P1 |
| 输入时序优势 | 可行 | tick 窗口 | 中 | P1 |
| late replay 时光倒流 | 默认不可行 | 默认关闭 | 高（开启后） | P0（开启前必须解决） |
| 宏/脚本/预输入 | 可行 | 未来 tick 上限 120 | 中低 | P2 |
| 会话劫持/踢人 | 可行 | 32 位 token | 高 | P0 |
| 登录洪泛/占坑 | 可行 | 无（登录在限流前） | 高 | P0 |
| 慢客户端拖垮快照 | 可行 | 全局 `waitsnd` 背压 | 高 | P0 |
| 畸形包/超长包 | 基本不可行 | 包级校验 | 低 | — |
| 客户端内存/DLL 注入 | 可行 | 无 | 高 | P2（平台级） |
| 指纹伪造 | 可行 | 自报字段 | 中 | P1 |

## 6. 改进路线

### Phase A：低成本、纯服务器、不改协议（建议先做）

目标：堵住最容易被利用、且不需要架构改动的洞。

1. **登录限流与占坑保护**
   - 按 IP / 全局的登录令牌桶。
   - 未认证会话短 TTL；未认证不占正式 slot。
   - 监控每 IP 并发登录数。
2. **per-peer 背压**
   - `send_snapshot_to_all` 不再用全局 `waitsnd`，改成逐会话判断。
   - 对长期超限的 peer 降级（降快照频率）或断开。
3. **输入 payload 上限**
   - 按 `MessageType` 限制最大 payload（输入 32B、快照 8KB、登录 1KB）。
4. **输入时序收敛**
   - 增加服务器侧 `min_input_lead_ticks`，拒绝贴脸输入。
   - 限制同一未来 tick 的覆盖次数。
5. **遥测**
   - 每会话记录：lead 分布、输入间隔、aim 变化率、late replay 次数、ACK 异常率、`waitsnd` 峰值。
   - 先只记录，不处罚。

验收：

- 新增单测：登录洪泛、慢 peer 隔离、最小 lead 拒绝、超长 payload 拒绝。
- 现有 `nsync_net_real` 回归不出现 corrections/desync 退化。

### Phase B：协议与会话安全（公开联机前必须）

1. 128-bit CSPRNG session token。
2. 包级 HMAC；进一步用 DTLS 或 libsodium 做加密。
3. token 绑定 peer，重连换 token，缩短重连窗口。
4. 登录挑战/响应或平台票据。
5. 协议版本升级，保留旧版兼容期或强制升级。

验收：

- token 不可枚举；抓包无法直接复用会话；重连从不同 IP 失败或被审计。
- 新增协议 fuzz 测试（畸形长度、截断、错 magic/version/token）。

### Phase C：架构级（反作弊收益最大）

1. **AOI/可见性裁剪**
   - 服务器按视野/距离/队伍过滤实体。
   - 输入广播只发给 AOI 内客户端。
   - 客户端改为“本地预测 + AOI 内远端预测 + AOI 外插值/冻结”。
   - 这会改变 `local_net` 的远端预测模型，需要单独设计文档。
2. **瞄准校验**
   - 开火时 LOS/FOV 校验。
   - 转向速率上限（可配置、可灰度）。
   - 统计检测：瞄准速度、跟踪误差、反应时间、爆头率、预开火。
3. **服务器录像**
   - 现有确定性 replay + 快照历史已经具备基础。
   - 建议按对局落盘输入流和关键快照，支持离线复现和人工复核。
4. **late replay 重新设计**
   - 限制到极短窗口，或只允许非战斗输入。
   - 加总预算和审计。

### Phase D：运营与响应

1. 指标看板：拒绝输入、限流、ACK mismatch、late replay、登录失败、`waitsnd`。
2. 可疑对局自动标记 + 录像。
3. 处罚/封禁工具链（至少支持按账号/设备/对局回放取证）。
4. 定期复盘作弊样本，反推新的检测规则。

## 7. 测试与监控建议

### 7.1 可复用的现有能力

- `nsync_net_real`：真实 UDP/KCP、loopback、RTT/丢包/抖动/重复/延迟尖峰、late input replay、sync time to step。
- `nsync_soak` / `scripts/*soak.ps1`：长时间、多对局、并发。
- `LocalClient::inject_desync()`：人为制造分叉，验证校正路径。
- `NetGraph`、`ClientStats`、`NetServerStats`：已有大量计数可扩展。

### 7.2 建议新增的“作弊客户端”测试

1. **时序作弊客户端**：固定最小 lead、覆盖未来 tick、发送迟到输入。
2. **输入洪泛客户端**：高 pps、超长 payload、错误 slot/按钮位。
3. **慢 ACK 客户端**：故意不 ACK，验证 per-peer 背压是否隔离。
4. **登录洪泛脚本**：多源端口并发登录，验证限流和 slot 保护。
5. **token 枚举脚本**：验证 token 随机性和重连绑定。
6. **自瞄模拟**：完美 aim + 触发开火，验证检测指标是否能区分。
7. **宏/脚本**：固定节奏连招，验证输入间隔/覆盖统计。

### 7.3 建议监控指标

| 指标 | 用途 |
|---|---|
| `rejected_slot_inputs` / `rejected_future_inputs` / `rejected_late_inputs` | 输入异常 |
| `rate_limited_packets` / `rate_limited_inputs` | 滥用 |
| `ack_mismatches` / `rewritten_ack_mismatches` | 状态分叉/迟到重写 |
| `late_replays` / `late_replay_failures` | 回滚压力 |
| 每会话 lead 分布、输入间隔方差 | 时序作弊 |
| 每会话 aim 角速度、aim 到目标夹角 | 自瞄 |
| 每 peer `waitsnd` 峰值/持续时间 | 慢客户端 |
| 登录尝试/IP、登录失败率 | 洪泛 |
| `action_mismatches` | 动作事件伪造/不同步 |
| 快照大小/生成耗时/广播耗时 | 容量与 DoS |

## 9. 需要先决策的问题

在动手改之前，建议先明确以下取舍，否则容易做出互相冲突的方案：

1. **是否要做 AOI？**
   - 做：反透视收益最大，但要改远端预测模型，工作量大。
   - 不做：接受“客户端必然知道所有位置”，把反作弊重点放在自瞄和会话安全。
2. **最小输入 lead 取多少？**
   - 太小：时序作弊空间大。
   - 太大：诚实玩家手感变差。需要实测 0/50/150ms 下的表现。
3. **late input replay 是否保留？**
   - 保留：必须解决“时光倒流”和 CPU 放大。
   - 删除：高延迟玩家体验变差，但安全性更好。
4. **会话安全做到哪一层？**
   - 只做随机 token + HMAC：成本低，但明文仍可被嗅探。
   - DTLS/加密：更安全，但引入依赖和性能开销。
5. **是否引入平台级反作弊？**
   - 服务器侧只能做行为检测；内存/注入最终需要客户端方案。
